# Harbor Health

An accessible patient portal and API starter for a small hospital. Patients can request appointments; doctors can review and update their appointments. The public website is designed with larger readable text, high-contrast controls, clear language, and responsive layouts.

## Run locally

Requirements: Node.js 20+ and a PostgreSQL database (Neon works).

1. Create a Neon project and copy its connection string.
2. In the Neon SQL editor, run [`schema.sql`](./schema.sql).
3. Copy `.env.example` to `.env` and set the variables below.
4. Run `npm install`, then `npm start`; open `http://localhost:3000`.

Generate independent secrets instead of reusing the example values:

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Use the outputs for `PASSWORD_PEPPER`, `TOTP_ENCRYPTION_KEY` (hex), and `AUDIT_HMAC_KEY`, respectively. Keep `.env` out of source control and store production values as Render environment secrets. Configure SMTP values to enable email verification and email one-time codes. Without an SMTP provider, registration and email-based sign-in intentionally fail closed.

## First accounts and administrator setup

There are no default users or shared passwords. Register and verify your first account using the website, then run the one-time bootstrap from a trusted operator machine with the production Neon connection string and audit key configured:

```powershell
$env:BOOTSTRAP_ADMIN_EMAIL = "verified-admin@example.com"
npm run bootstrap-admin
Remove-Item Env:BOOTSTRAP_ADMIN_EMAIL
```

The script promotes only that verified account, refuses to run if a super administrator already exists, and records the bootstrap in the append-only audit log. Sign in, then use **Administration** to review doctor registrations, deactivate accounts, and assign the separate `admin` and `super_admin` roles. Register additional patient/doctor accounts normally; do not insert demo credentials into production.

## Deploy

- **Neon:** use a dedicated, least-privileged database role and a TLS connection string. Run `schema.sql` as a migration using a migration-capable database role, not the runtime role. Keep Neon branch/schema changes separate from production data.
- **Render:** deploy the included [`render.yaml`](./render.yaml) blueprint, set `APP_ORIGIN` to the service's exact HTTPS origin, and fill in all secret environment variables in Render. The app serves the website and API from one origin.
- **Mobile app:** the API is JSON-based and same-origin-cookie authenticated for the web. A mobile client should use a separate secure token/session flow rather than storing the browser cookie or embedding server secrets in the app.

## Security features

- Argon2id password hashes use per-password salts generated by Argon2 plus an independently stored server-side pepper. The pepper is concatenated before hashing and must remain outside the database.
- Email verification and email sign-in codes expire after 2 minutes; authenticator TOTP uses a 120-second period. The setup page provides a QR code and requires a valid code before enabling TOTP. TOTP secrets are encrypted at rest with AES-256-GCM.
- Sessions are opaque, random, stored as SHA-256 digests, expire after 8 hours, and use `HttpOnly`, `SameSite=Lax`, `Secure` production cookies. Mutations require a per-session CSRF token. Authentication endpoints are rate-limited.
- Registration can create only `patient` or `doctor` accounts. New doctor accounts require email verification and administrator approval before sign-in or appointment assignment. `admin` and `super_admin` are distinct administrative roles; do not grant either through public registration. Use the one-time bootstrap script for the initial super administrator; only `super_admin` can change roles afterward.
- User removal is a soft delete; the account is deactivated and sessions expire, while records remain. Appointment access is scoped to the patient, assigned doctor, or administrator. Audit entries are append-only at the database trigger layer and HMAC-chained by the service.
- Helmet security headers, input validation, parameterized SQL, size limits, TLS, generic login errors, and explicit error responses are enabled.

## Backup and restore

For a large, growing medical-record database, use **Neon's managed backup/PITR and branching** as the automated recovery mechanism. Enable the desired retention in Neon, verify it in the Neon project settings, and periodically exercise point-in-time recovery by restoring to a **new branch/database**. Validate that branch before changing the Render `DATABASE_URL` configuration to point the application at it. This switches which database configuration the app uses; it does not overwrite or delete the source database. Keep the original branch until recovery has been reviewed.

Render's local filesystem is not a durable backup target. Do not back up PHI to local files, commit secrets, or use the app to overwrite production data during a restore. Recovery retention and point-in-time window depend on the selected Neon plan; confirm the current plan's limits. Configure database monitoring, restricted credentials, encrypted transport, retention, and restore drills before storing real patient data.

## Before production use with patient information

This is a starter, not a certified clinical system. The dashboard includes illustrative sample appointments and medication reminders; they are not real patient records and are not backed by clinical APIs. Complete a privacy/security assessment, legal and regulatory review (including applicable healthcare and data-protection requirements), threat modeling, penetration testing, incident-response planning, clinical workflow validation, accessibility testing, and an external backup/restore drill. Use synthetic data until those checks are complete. Production admins and demo users are intentionally not seeded with weak or shared passwords.
